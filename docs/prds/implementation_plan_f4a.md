# Bedrock credentials, configuration and interaction

[Bedrock requirements](implementation_plan_f4.md) · [Account selection](implementation_plan_a2.md)

## Agreed acquisition names

- [x] Use provider-local BEDROCK_AUTH_MODE=session|access_key|api_key. Session selects SDK/profile credentials and the configured direct/federated acquisition path; access_key retrieves username as access key ID and password as secret access key; api_key retrieves only password as a Bedrock bearer key, without requiring username. Existing GPT_AUTH_MODE remains provider-owned. Authentication names do not select subscription billing. Three-mode naming and fields are agreed; controlled bearer runtime and remaining live acceptance are tracked under the [Mantle migration](implementation_plan_f4d.md).
- [x] Include Bedrock bearer API keys as a distinct api_key mode. This supersedes their earlier initial-scope deferral. Never reinterpret access_key as a password-only bearer token or silently substitute one credential source for another.

- [x] Default BEDROCK_PROFILE to the AWS named profile `default` and BEDROCK_REGION to `us-east-1`. Explicit nonempty values override these defaults; explicit blanks restore SDK profile resolution (including AWS_PROFILE) and region resolution respectively. The nonempty defaults take precedence over those SDK settings. Shared LLM_PROVIDER help identifies bundled GPT as default and supplies both bundled factory selectors.

## Remaining contract decisions
- [ ] Resolve the existing accounting vocabulary for metered AWS usage: qualify the generic metered meaning of api_key or introduce a validated versioned value. Profile/browser/SSO credentials do not imply prepaid subscription billing. Do not apply subscription quota or pay-period conversion to Bedrock; unavailable charge information remains explicit.
- [ ] Agree which direct AWS, IAM Identity Center and optional federated-helper paths are supported, the profile/identity binding for indexed accounts, secret-field representation for temporary session tokens and persistence policy. Record unsupported/deferred forms instead of silently substituting credentials or methods.

## Credential acquisition

- [x] Deliver the [replaceable acquisition foundation](implementation_plan_f4a1.md): lazy adapter selection, typed context/material, owned refreshable temporary credentials and SDK-worker isolation. Concrete direct/federated adapters and live identity qualification remain separate.
- [x] Define a replaceable session-credential acquisition interface before implementing login automation. The existing SDK chain, direct AWS login, IAM Identity Center and optional federated helpers are separate adapters behind this interface; a different identity provider must be selectable without changing catalog, Mantle transport or the password-manager contract. Pass an explicit selected-identity binding, role-bound secret reader, interaction owner and cancellation/deadline context. Return provider-owned opaque credentials with refresh/expiry and disposal; expose typed interaction-required and authentication failures rather than raw helper output. Keep the acquisition adapter choice separate from BEDROCK_AUTH_MODE and UNATTENDED_USER_INDEX. Indexed session acquisition must use this interface and may not silently use unrelated ambient credentials. The initial preauthenticated slice rejects indexed session mode until this binding is implemented.
- [ ] Reuse the declared LLM User role, selected password manager and optional shared zero-based UNATTENDED_USER_INDEX. Retain central pairing/ambiguity checks and selected identity through retries and refresh. A vault item name is not an AWS profile or account identifier. Bind the configured account to a non-secret expected profile/identity without storing returned secrets in ordinary configuration.
- [ ] Support documented SDK credentials, including selected/default profiles, temporary sessions and relevant role/process providers. Retain the agreed provider profile/region default and explicit-blank precedence above. Bound discovery and errors. In indexed unattended operation, unrelated ambient credentials must not override the selected credential source; validate the effective identity without exposing it in public fixtures/artifacts.
- [ ] For access-key acquisition, retrieve access key ID from username and secret access key from password through the selected LLM User reader. Temporary credentials also require a session token and expiry; do not accept an incomplete tuple or overload the TOTP field. Extend generic secret retrieval minimally if selected, or document the initial limitation. Never print, persist in dotenv, or include retrieved key IDs/secrets/tokens in ordinary evidence.
- [ ] Implement api_key acquisition by retrieving the password as a Bedrock bearer key without requiring an IAM key ID. Qualify short-term and long-term key behavior and expiry for Mantle catalog/inference; report unsupported/expired forms without falling back to another credential source. Keep keys scoped to the provider instance instead of changing process-wide environment for unrelated consumers.
- [ ] Deliver the [attended native direct/Identity Center milestone](implementation_plan_f4a2.md), separately from indexed automation and live acceptance. Direct browser-based login must establish SDK-usable temporary credentials through a documented acquisition route; console cookies alone are insufficient. Keep AWS console-session login distinct from IAM Identity Center. Validate CLI/SDK prerequisites and permissions, cancellation and browser handoff. Reuse existing UI ownership/visibility policy rather than creating untracked sessions.
- [ ] Integrate the optional [aws_okta_keyman fork](https://github.com/gorban/aws_okta_keyman) through an independently verified, version-pinned Python input/challenge seam. Verify this fork's factor ordering against pinned source/tests; its README alone does not establish TOTP preference. Support username/password, available TOTP, account/role selection, temporary credentials and refresh. Prefer supported TOTP before push/number challenges; preserve interactive handling of other required factors. Keep deployment-specific URLs/accounts/roles outside public examples. Preserve its [Apache-2.0 license and notices](https://github.com/gorban/aws_okta_keyman/blob/master/LICENSE.txt); avoid unnecessary vendoring. Optional installation/selection does not waive implementation acceptance of this helper.

## Interaction, lifecycle and isolation

- [ ] Attended acquisition asks one required value at a time through the running TUI or visible authorized browser flow. Indexed unattended acquisition fills available values from the selected reader and retrieves fresh TOTP only when challenged. If a required value/factor is unavailable and interaction is permitted, request explicit attended completion for the same identity. This does not clear the index, switch accounts or convert an explicitly configured failed source into another auth method.
- [ ] With NO_STD_IN or no interaction owner, raise a typed actionable interaction-required failure; never block a server worker, SDK thread or helper on hidden stdin. Bound attempts and allow cancellation. Do not suppress a required MFA challenge or treat an existing login as proof of the intended identity.
- [ ] Keep credentials in a provider-owned opaque, callable/disposable session shared by catalog and inference. Coalesce setup/refresh, reject expired or closed sessions, and isolate simultaneous accounts/regions/profile choices. No AWS calls or login during help, schema/config inspection, collection or cached cost prediction.
- [ ] Agree helper/profile persistence and atomic/concurrent updates before implementation. Preserve unrelated AWS profiles and existing credential files. Scope subprocess environment, redact stdout/stderr/errors, and bound refresh/process lifetime, cancellation and cleanup. Do not assume a helper supports credential_process without verifying its documented JSON/expiry protocol.
- [ ] Qualify direct AWS and federated adapters separately, each with attended and indexed unattended scenarios, missing-factor handoff, refresh, cancellation and identity isolation. First close focused offline contract tests, then pause for the user to prepare each real account and confirm readiness for live authentication. Obtain separate explicit approval before each new integration test that can incur inference charges. A successful preauthenticated profile or access-key test does not close these login-automation scenarios.

Use [Boto3 credentials](https://docs.aws.amazon.com/boto3/latest/guide/credentials.html), [AWS console login](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html), [IAM Identity Center login](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html), [process credentials](https://docs.aws.amazon.com/sdkref/latest/guide/feature-process-credentials.html) and [Bedrock API-key contracts](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-use.html) as the public protocol basis. Pin and test supported versions during implementation.
