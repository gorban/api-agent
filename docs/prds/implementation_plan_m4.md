# Ordered resource-pack composition proposal

[Provider composition](implementation_plan_m.md) · [Declaration ownership](implementation_plan_b.md)

This is a proposed contract, not implemented launcher syntax. Existing single-pack behavior remains the compatibility baseline. No application may claim multi-pack acceptance from provider configuration lists or a selected workflow library alone.

## Selection and immutable ownership

- [ ] Admit an explicit ordered list of selected packs, shared contributions first and final application contribution last. Reject empty selection, repeated physical roots, duplicate pack IDs, cycles and unsupported declaration versions before installation, imports or startup. Do not discover sibling packs or activate an omitted pack.
- [ ] Retain a contribution object for every pack: validated ID, canonical physical root, owner root, source/installed provenance, immutable manifest identity and its captured declarations. Keep each path paired with its declaring owner. Equal relative paths in different packs are distinct resources; deduplication may only collapse a verified identical physical contribution.
- [ ] Keep runtime root, launcher root, final application owner and each pack root distinct. The final contribution owns application identity and default test selection. Preserve explicit launcher origin and configuration provenance. Single-pack save ownership remains unchanged; the multi-pack save policy below must not implicitly grant write authority to a base contribution.
- [ ] Specify selectors in a separate reviewed parser change. Repeated directory options are a candidate, not an existing interface. Environment selection must be unambiguous and cannot silently append packs. Preserve the existing one-directory option, separator handling and relative-path semantics.

## Composition rules

- [ ] Compose configuration declarations in selected order, then explicit provider declarations using existing override authority and constraint checks. Defaults may override earlier valid defaults. Replacing an existing field requires explicit authority and cannot weaken safety constraints. Retain the contributing ID and path in diagnostics and effective-value provenance.
- [ ] Preserve single-pack configuration behavior exactly: read runtime dotenv, declared additional dotenv paths in declaration order, launcher dotenv, then selected external-pack dotenv, deduplicating paths by first occurrence before reads; environment and CLI retain their existing precedence. For the bundled demo, retain runtime dotenv behavior and exclude demo-root `.env` from reads and save-target alternatives. Keep the current launcher-dotenv default save target, all existing target alternatives, explicit target switching and persistence that moves saved keys from overlapping alternate targets, including rollback behavior. Do not apply the proposed multi-pack policy to a one-pack invocation.
- [ ] For multi-pack reads, propose runtime dotenv, then each contribution's declared additional dotenv paths in selected-pack/declaration order, then launcher dotenv, then each selected pack's own dotenv in selected order, followed by environment and CLI. Deduplicate paths by first occurrence before reading; later distinct files override earlier files. Bind additional paths to their declaring owner. This explicit order places launcher values below pack-root values and must be shown in configuration review, including alias cases.
- [ ] For multi-pack writes only, propose the final application's dotenv as the default save target. Keep runtime, base-pack and additional dotenv inputs read-only by default, even when they contain overlapping saved keys; never delete those keys as an implicit save side effect. Offer explicit selection of the launcher or another admitted target and an explicit move-versus-copy choice, displaying every affected file. An explicit move authorizes removal only from its selected writable source targets; unselected/read-only inputs remain unchanged. Report any retained higher-precedence value that prevents a save taking effect. Reject writes to installed/nonwritable targets. These proposed choices require a reviewed session/API policy and compatibility tests before implementation; they do not redefine existing single-pack switching or moves. Preserve credentials and omit dotenv contents from composition reports.
- [ ] Preserve additive provider/configuration/dependency contributions with their owners. A later selected factory must carry its own declaration closure; reject cycles, conflicting factory/catalog identities and stale selections before invoking factories. Identity adapters and singleton UI/API selections require explicit replacement rather than accidental last-wins behavior. An omitted API stays absent; no missing endpoint may select the bundled demonstration API for an external composition.
- [ ] Expose selected test suites with owner identity. Keep runtime units plus all selected pack units; final application integration/E2E suites remain the default, with explicitly selected shared suites available. Preserve each owner's coverage scope, marker and confirmation requirements. Aggregate production directories and dependency manifests only from admitted contributions.
- [ ] Compose infrastructure/tool declarations by stable IDs. Reject collisions unless the contract explicitly authorizes a replacement; validate replacement compatibility and preserve dependency closure. Resolve activation and endpoints from the admitted composed configuration. Never merge detached paths under the final pack root.

## Executable resources and installed delivery

- [ ] Give every executable graph/resource an explicit owner identity. Preserve existing `base`/`pack` semantics for single-pack callers; introduce a versioned owner map for multiple packs rather than reinterpreting `pack` according to traversal order. Imports, prompts, native functions, nested graphs and replacements resolve against their declared owner and captured source inventory.
- [ ] Select one root workflow explicitly. Ordered replacements must name a target owner and stable graph identity; reject ambiguous, duplicate, unreachable or unowned targets. Preserve shared workflow contributions unless an explicit replacement permits otherwise. Do not concatenate pack trees or copy source into a synthetic combined directory.
- [ ] Capture and verify all selected source files before executable admission and again at existing verification boundaries. Preserve regular-file, traversal, symlink, mutation and bounded-read checks. Installed contributions must be owned by their verified distribution inventory; reject ambiguous distributions and unowned files without importing package code. Preserve third-party notices and source-independent installed execution.
- [ ] Serialize the complete ordered selection, root/owner identities and launcher origin through interpreter preparation, process handoff and child execution. A relaunch must restore the same admitted composition and reject changed manifests or roots before effects. Include all admitted dependency manifests in the environment fingerprint; changing a shared contribution must invalidate stale preparation.

## Implementation and acceptance sequence

- [x] Independently review this proposed ownership, precedence and admission contract. This review does not implement multi-pack selection or runnable launchers.

- [ ] First add inert owner/contribution carriers, loader validation and composition reporting. Keep help, collection and review free of authentication, inference, factory imports and infrastructure effects.
- [ ] Then implement configuration/provider/dependency composition and handoff; then graph/resource ownership and infrastructure/tool composition; finally executable launcher consumers. Do not advertise partially supported compositions as runnable.
- [ ] Add independently authored two-pack and three-pack fixtures covering inherited behavior, explicit replacement, duplicate IDs, path ownership, schema weakening, environment/CLI precedence, absent-API failure, cancellation and failed cleanup.
- [ ] Prove bundled-demo `.env` exclusion and single-pack read order, launcher-default save ownership, explicit target switching, overlapping-key moves and rollback remain equivalent. Prove proposed multi-pack additional/launcher/root read order, aliases, read-only inputs, explicit target/move choices and effective-value diagnostics. Prove exact ordered resolution from an unrelated working directory, source checkout and relocated installed artifacts, including interpreter relaunch. Mutate ordering, owner binding and serialization independently to establish causal rejection tests.
- [ ] Run applicable unit tests with exact line/branch coverage, installed/lifecycle tests, boundary checks and independent contract/runtime review. Human acceptance and publication remain separate. No implementation or runtime-review gate is complete in this proposal.
