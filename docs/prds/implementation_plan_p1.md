Additional executables are prepared for selected operations rather than requiring the whole tool inventory upfront. This migration does not promise a minimal TUI-only Python closure or external access.

## Entrypoint and CLI contract

- [ ] Make `launch.sh` the sole root launcher; move Python entry behavior into the package under `src/api_agent/` and remove the root `launch.py` as part of the completed migration. Keep the shell wrapper small: locate the source entry, invoke controlled mise preparation/execution, and forward application arguments to the existing Python parser. Do not duplicate configuration or `.env` parsing in shell.
- [ ] Preserve every currently supported application option, alias, positional selector, argument order, empty/quoted/spaced value and `--` delimiter through literal `"$@"` forwarding. Do not build command strings, use `eval` or apply shell expansion to application argument contents. Existing `./launch.py ARGS` invocations become `./launch.sh ARGS`; `python launch.py ARGS` becomes a shell invocation rather than `python launch.sh`.
- [ ] Preserve caller CWD and all declared path anchors, configuration precedence, source/pack selection, launcher provenance, terminal stdin/stdout/stderr, automation behavior and application exit codes. Select the intended mise configuration without changing the meaning of caller-relative CLI paths. Define tool-version/configuration ownership and verify an alternate selected source uses its appropriate runtime.
- [ ] Preserve interrupt/signal delivery and existing cleanup ownership through bootstrap, preparation, interpreter handoff and execution. Reuse bounded progress/cancellation interfaces; installation failure must not silently continue with incompatible tools.
- [ ] Update source-root detection, interpreter relaunch, pack handoff contracts, packaging/build declarations, help, docs and checks that currently depend on the root `launch.py` path. External pack compatibility uses generic interfaces; pack-owned code remains outside the base repository.
- [ ] Support extracted archives without Git or `.git` for ordinary startup/configuration. Keep existing worktree verification for actual Git checkouts and provide explicit archive-compatible workflow/asset behavior. Do not fabricate repository history or claim a Git archive is a verified checkout. Git-dependent features declare their own requirement; automatic Git installation is not assumed or promised without a separately qualified acquisition path.
- [ ] Reject an existing `.venv` that uses a different base interpreter from the mise-selected Python. Preserve that environment and give move-aside/recreate guidance rather than deleting it or silently bypassing tool selection.
