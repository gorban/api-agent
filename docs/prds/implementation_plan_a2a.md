## Interactive password-manager recovery

- [x] Define an optional manager recovery capability and an operation-owned interaction interface. Existing command/parser implementations remain valid without it and retain their current error behavior. Consumers continue requesting username/password/TOTP through the same helpers, passing only the optional interaction context. Manager-specific classification and recovery policy belong to the adapter; the common runner owns processes, interaction transport and cleanup.
- [x] Implement Keeper logged-out classification, including its noninteractive persistent-login failure and interactive authentication prompts. Preserve a safe typed login-required explanation through username retrieval, provider setup and failure reporting. Do not replace unrelated lookup, executable or implementation failures with a login request. Start with Keeper; retain unenriched 1Password and synthetic pack adapters as compatibility cases.
- [x] Relay recovery through terminal output/input when NO_STD_IN=True, without requiring isatty() or rejecting solely because stdin is redirected. This is an intentional exception to launch configuration's noninteractive behavior. Display login output before waiting; accept supplied stdin until authentication completes, EOF, cancellation or an enclosing deadline. EOF must fail actionably. Do not change test-execution acceptance rules. Use the terminal semantics required by the manager internally; Keeper needs a pseudo-terminal for its terminal check and getpass behavior.
- [x] Add a temporary recovery screen titled with the manager name: scrollable read-only Output, Input, Send value (Enter), and Cancel. Accumulate authentication output and mask secret entry. After submission, retain the masked input read-only and disable Send until more visible login output arrives; then clear/re-enable Input and Send. Keep Cancel and Ctrl+R available while waiting, preserve confirmation focus, and clear retained input when the screen closes. Reuse established edit-screen focus/Enter behavior. Cancel has no letter shortcut and requires explicit y confirmation; terminate and reap the invocation before dismissing. Ctrl+R retries the same credential request only after disposing its prior invocation; reject late events from that invocation.
- [x] Keep credential-result stdout separate from the interactive login transcript. Never forward retrieved passwords/TOTP, entered secrets or transcript contents to test stdout, trace events, logs, Allure, snapshots or readiness/error IPC. Live login output is available only through the dedicated interaction boundary; use bounded output and terminal-control handling. Return the requested credential only to its scoped caller after successful recovery.
- [x] Serialize recovery for the same operation-owned manager/session, retrying queued retrievals after recovery so they can use the authenticated session without another prompt. Present different sessions one at a time. Do not share retrieved secret values or TOTP codes. Wire the interaction boundary through ordinary shared setup and worker-local DEBUG ownership without changing captured manager definitions or account binding. Canceling a queued credential request must not cancel another request’s active invocation. Canceling its active owner disposes that invocation before the next queued request retries; readiness consumers retain shared-setup cancellation shielding. Operation shutdown cancels and synchronously drains all owned processes and pending interactions.
- [x] Separate short retrieval execution from human recovery timing using the shared component timeout/progress interface. Human input must not be limited accidentally by the existing 15-second retrieval budget; active recovery still respects applicable enclosing deadlines. Queueing, retries and incorrect-password loops must not restart or extend the enclosing operation budget. Report the active component to the test row.
