# Studio response identity and selection records

[Studio frontend](implementation_plan_i2a.md) · [Model selection](implementation_plan_f2f.md) · [Local application](implementation_plan_h1a1.md)

Run local review found a concrete selected model sent over HTTP but displayed as a requested provider default, plus empty metadata rows for values absent from the response contract. This repair concerns presentation and immutable browser records, not inference selection or accounting semantics.

- [x] For new requests, record the model actually selected and sent. If Settings visually preselects a catalog model and HTTP sends its concrete ID, do not label that request as an unspecified model. Preserve an explicit family choice, omitted version intent and requested effort separately from the resolved concrete model snapshot. Retries retain the original snapshot; do not rewrite old messages' missing selection intent using today's catalog.
- [x] Retain the exact provider-reported model ID. An exact match against the catalog captured for that request may supply friendly family and version interpretation, clearly labeled as catalog metadata for the reported ID rather than an independently reported revision. Freeze that interpretation with the message so settings/catalog changes and reloads cannot rewrite history. Never borrow the requested model's version when a different or unknown ID was reported, or guess a version for an unversioned model.
- [x] Omit absent optional reported reasoning, version, serving revision and service-tier rows instead of filling the panel with unsupported placeholders. Retain and display valid values when available. Requested reasoning is not proof of effective reasoning, and token counts cannot establish the applied effort. Preserve diagnostic raw IDs and useful known-versus-unavailable distinctions without fabricating metadata.
- [x] Retain existing optional public result fields for actual model, service tier and serving revision: these have provider/result/HTTP forwarding and accounting uses. This repair adds no redundant generic version/reasoning DTO fields, removes no useful provider contract and does not equate a backend fingerprint with a serving revision.
- [x] Verify real controlled browser requests for initial preselection, explicit family with omitted version and reasoning, different/unknown reported IDs, unversioned catalogs, optional fields, retry, changed settings/catalog and reload. Assert exact metadata labels/values and unchanged outbound model/effort. Use causal controls for selection recording and frozen reported-catalog interpretation.
- [x] Renew applicable exact frontend/unit coverage, packaged/installed asset and notice checks, public source/index/metadata gates and independent/external review before delivery. No live inference is required for this display repair.
- [x] Human acceptance of the repaired metadata during Run local, recorded October 23, 2026. Core Run local acceptance is recorded separately in [H1a1](implementation_plan_h1a1.md); tracing and product integration retain their own gates.
