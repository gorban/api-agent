# Included personal GPT LLM provider

This is the early exception to deferred public demo applications. Build a replaceable included provider, not inference code inside orchestration. First complete [consumer contract hardening](implementation_plan_m3.md); apply [shared adapter requirements](implementation_plan_f1.md). Actual live GPT calls need the user's personal credentials and reviewed settings.

## Checklist

- [x] Agree the authentication/API matrix with the user: support API-key access with `completions` or `responses`, and eligible subscription integration with `responses` only. Reject subscription plus `completions`; this approves the design, not a live call or completed implementation.
- [ ] Implement provider-contributed `GPT_AUTH_MODE` (`subscription`, `api_key`) and `GPT_API_MODE` (`completions`, `responses`) in `llm-providers/gpt-provider/cfg/config.toml`, not shared core configuration. Default authentication to subscription for the preferred personal-plan route; conditionally default the API to responses for subscription and completions for API-key access. An explicit API value takes precedence and is never silently changed to repair an invalid combination.
- [ ] Contribute `GPT_API_KEY` and `GPT_BASE_URL` through that same provider declaration. The key may be omitted or explicitly empty in subscription mode; API-key executable operations require a nonempty key. Only API-key mode uses that key, without a browser login or indexed vault role. Additional subscription-only settings are applicable/required only for subscription operations that need them; generated OAuth registration/session state stays provider-owned rather than becoming manual API-key-mode prerequisites.
- [ ] Validate the resolved combination before opening clients/browsers or making requests, including explicit .env, environment and CLI overrides and TUI mode changes. Subscription plus completions raises a useful configuration error naming both fields and supported alternatives. Reject unknown enum values, invalid endpoints and missing applicable credentials separately; help/collection never authenticates. Do not use an API key as fallback when subscription login fails, or a subscription token when API-key mode is selected.
- [ ] Establish `llm-providers/gpt-provider/`, an importable `gpt_provider` package, adjacent typed configuration, distribution/dependency metadata and independently authored contract tests. Load it through the ordinary LLM factory contract; support source and relocated installed use. Inclusion does not select it for unrelated operations.
- [ ] For the API-key route, contribute endpoint, secret API key and GPT selection settings. Authentication requires no login browser or indexed password-manager account: omit the optional hook or implement an explicit async no-op, and supply the configured bearer key on each authorized request. Register secrets before diagnostics. Keep endpoint/key overrides reviewed and avoid exposing the key in traces, URLs or artifacts.
- [ ] Implement eligible subscription OAuth registration/consent, account selection, token lifetime and Responses streaming inside this provider. Verify preview feature/parameter limits against required tools and structured output, rejecting unsupported requests rather than ignoring parameters. Use the documented public subscription endpoint with store=false and stream=true; never send its OAuth token to a configurable third-party endpoint. Do not scrape another application's auth cache. Report limits and unavailable cost data honestly; eligibility and actual account access require live verification.
- [ ] Implement both API-key transports, mapping `completions` to `/chat/completions` (not legacy `/completions`) and `responses` to `/responses` under the configured API base. Share common LLM results/events/usage while preserving format-specific payloads internally. Validate the chosen endpoint/selection's supported features; a valid authentication/API combination does not guarantee every compatible service implements both formats.
- [ ] Support GPT-only discovery/selection, completion, streaming, tools and structured output where advertised. Translate transport-specific messages/events/usage into the shared schemas. Reject unsupported features or selections; do not silently fall back to another LLM family.
- [ ] Prepare selected dependencies from either launcher through managed bootstrap in its venv. Do not require manual installation of an editable sibling or unrelated optional providers.
- [ ] Normalize usage and provider-owned cost estimates without inventing prices or zero cost when unavailable. Keep personal inference accounting separate from any external access adapter's quota snapshots. Preserve the exact selected GPT throughout workflow personas.
- [ ] Test API-key header forwarding, absent/no-op auth, zero browser/credential retrieval, supported feature rejection, stream early close, deadlines, errors, privacy and disposal with controlled transports. Compare the same consumer with a second synthetic LLM adapter.
- [ ] Cover all four authentication/API combinations with deterministic tests: three accepted, subscription/completions rejected before any side effect. Test omitted/empty/nonempty keys in both auth modes, conditional defaults and explicit overrides, no credential fallback, inactive subscription settings, OAuth endpoint binding and both transports through one unchanged renderer. API mode/account changes cannot reuse stale clients or auth sessions. Complete applicable unit/coverage checks before code commits.
- [ ] Human-review contributed settings and personal funding/transport, then verify no-inference discovery before the first small personal GPT renderer call. Record integration/E2E history from the first live run, preserving interactive gates and human E2E acceptance.

This task chooses no particular GPT variant and makes no live call. Demo UI/API implementations remain deferred and are not prerequisites for this provider.

## Configuration acceptance matrix

| GPT_AUTH_MODE | GPT_API_MODE | Configuration rule |
| --- | --- | --- |
| subscription | responses | Valid with eligible integration/account; GPT_API_KEY may be empty/omitted and is unused |
| subscription | completions | Invalid; fail before OAuth/client/request activity |
| api_key | responses | Valid with a nonempty GPT_API_KEY and supporting endpoint/selection |
| api_key | completions | Valid with a nonempty GPT_API_KEY and supporting endpoint/selection |

All GPT settings are provider-contributed and use normal effective-pack defaults and .env/environment/CLI precedence. Runtime flag availability follows provider implementation and selection; this checklist alone does not add executable settings.
