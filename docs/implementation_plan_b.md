# Declarative executable descriptions

## Checklist

- [ ] Define declarative formats for configuration and LangGraph flow, and identify other behavior that should use executable descriptions during planning.
  - [ ] Require a type for each configuration value and describe whether it is optional and whether it has a default. Use these declarations for the TUI/application type checks, missing-value handling, environment/CLI mapping, and generated configuration documentation.
- [ ] Compose shared configuration declarations with only the selected resource pack's extensions; do not require or prompt for another pack's configuration. Declare test-owner identity/root and per-mode test paths in the pack description. Pack unit paths are optional; unit mode always includes the base api-agent unit suite. Integration/E2E suites are selected by the pack.
  - [ ] Support a pack-launcher-only typed directory setting `API_AGENT_DIR` / `--api-agent-dir` (also `--api_agent_dir`) defaulting to `../api-agent` relative to that pack's root. It locates the base runtime and is not a required setting for launching api-agent directly.
  - [ ] Resolve this bootstrap setting before loading the base runtime, applying pack-root `.env` < environment < CLI precedence and anchoring relative values to the pack root. Keep bootstrap resolution noninteractive; validate the resolved base entry point and report how to override an invalid path. Share the bootstrap logic between pack launchers without copying the full TUI/config implementation. After loading the base, retain the value/source for normal declarative configuration handling.
- [ ] Resolve hierarchical defaults from shared declarations followed by selected-pack default overrides, then apply explicit values in `.env` < environment < CLI order. Pack defaults are still defaults, not explicit user input; validate them against the shared field type and retain source provenance for generated docs and TUI display.
  - [ ] Resolve controlling options first, then determine which conditional settings apply to the selected mode/features. Prompt or aggregate errors only for active required settings; inactive API/database/UI/Langfuse fields must not block startup. Re-evaluate applicability when a controlling choice changes.
  - [ ] Include `RUN_UI`, `UI_SOURCE_DIR`, and `UI_NX_APP`. Require UI configuration for E2E execution and local-run with `RUN_UI=True`, using selected resource-pack defaults where declared. Unit and integration tests do not require UI configuration regardless of `RUN_UI`. Declare the path anchor for each directory default/override explicitly so launcher-root UI paths and pack-root base/API paths do not depend on the current working directory. See [infrastructure/UI configuration](implementation_plan_h.md).
- [ ] Parse these descriptions programmatically at runtime to configure the application and construct the executable LangGraph flow.
- [ ] Derive configuration documentation and flow diagrams from the same descriptions, avoiding separately maintained representations that can drift out of sync.

- [ ] Define a human-readable Layout file as the executable source of truth for graph structure, data bindings, retry groups, and prompt composition. Review the concrete syntax with the user.
  - [ ] Resolve named Python node and condition functions through a function registry and construct/compile LangGraph nodes and unconditional or conditional edges at runtime. Report unknown function references and invalid layouts before execution.
  - [ ] Declare input/output reference IDs. Bind an input to a matching output from an earlier executed node; where no previous output supplies it, require the runner to supply it (for example conversation history, user prompt, or UI context). Report missing required inputs. Preserve the distinction between tool results and user-provided content.
  - [ ] Declare sub-groupings with their own bounded loop behavior, condition function references, and attempt budgets. Support a planner/plan_verifier group with an initial attempt and one retry, and a later graphql_executor/graphql_verifier group with its own independent attempts. Define success and exhausted-attempt exits; group retries must not consume another group's budget. These verification loops are distinct from exception retry policies.
  - [ ] Include an ordered prompt section containing file links. Each entry applies unconditionally or has an optional named condition function deciding whether it applies. Apply included prompts in declaration order.
  - [ ] Support the special path variable `<resource_pack>` in prompt paths, resolving it to the selected resource pack directory. Use whatever is selected by `--resource-pack-dir`, or an included demo resource pack by default for standalone api-agent. Report unresolved variables and missing applicable prompt files.
- [ ] Generate the human-readable flow documentation/diagram from the same Layout loaded by the runner. The Layout describes orchestration; named function implementations remain Python code.
- [ ] Add targeted integration coverage for conditional routing, output-to-input and runner-provided bindings, independent group retries/exhaustion, ordered conditional prompts, and switching between demo and selected resource packs. Establish [Allure reporting](implementation_plan_d.md) before writing these tests.

Implementation reference: [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) provides programmatic nodes, conditional edges, graph state, and loops. The Layout format and loader are project features to build on that API.

- [ ] Declare `TUI_MODE` as required when `NO_STD_IN=True` unless `HELP=True`, and preserve whether its test-mode value came explicitly from `.env`/environment/CLI for unit-only picker bypass and positional selectors; integration/E2E execution always stops at the filtered interactive test picker. Make `E2E_RERUNS` applicable only to E2E; unit/integration have no retries.

- [ ] Describe the conditional local-run `RUN_LOG_SOURCE` default in executable configuration: `all` when `NO_STD_IN=True`, otherwise `agent`, subject to pack defaults and explicit value precedence. Validate named sources against active service declarations; menu numbers are not configuration values. Use this default through both TUI and unattended launch paths.

- [ ] Declare boolean `HELP` and `COLLECT_ONLY`, both defaulting to `False`, including the special `-h` alias for `HELP=True`. Resolve the help short-circuit before execution configuration checks, and make collection-only validate only active collection requirements. Preserve explicit mode provenance so collect-only can bypass all interactivity when a test mode is supplied through `.env`/environment/CLI.

- [ ] Reject `NO_STD_IN=True` for integration/E2E execution as an incompatible configuration before startup. Keep `HELP` and configured-test-mode `COLLECT_ONLY` as nonexecuting, noninteractive shortcuts; collection does not require execution acceptance.

- [ ] Declare typed `UNATTENDED_AUTH` credential-source profiles (compact JSON object) and optional `UNATTENDED_SECONDARY_USER` role label. Use shared/demo no-secondary defaults and optional selected-pack secondary-role defaults, with explicit overrides; apply only selected profiles when validating setup. Derive both configuration cleanup and unattended-auth setup fields from these executable declarations. See [authentication setup](implementation_plan_a2.md).

- [ ] Declare `E2E_BROWSER_RESOLUTION` (validated `WIDTHxHEIGHT`, default `1440x900`) and boolean `E2E_DEBUG=False`. Add declarative field presentation metadata to exempt the debug default from startup default-configuration prompts without removing its ENV/CLI/help/cleanup support. Validate debug's strict-subset requirement at E2E start. See [Playwright E2E plan](implementation_plan_a3.md).

- [ ] Declare `AUTH_BROWSER_DEBUG=False` for explicit headed/retained authentication-browser debugging, distinct from subset-only `E2E_DEBUG`. Allow packs to declare an authenticated-UI launcher handler while keeping their application-specific login logic outside api-agent.
