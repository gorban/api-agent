# Content logging and trace scrubbing

## Checklist

- [x] Human approval (2026-10-05): the implemented privacy emission boundary is accepted: content defaults off; explicit LOG_CONTENT opt-in still scrubs credentials/registered secrets. Actual diagnostic and tracing consumer wiring remains below.

- [x] Before the first traced "Ok" run, declare shared boolean `LOG_CONTENT`, default `False`, through the runtime configuration system. Accept only the established `True`/`False` syntax. Only an effective, explicitly supplied `True` from `.env`, environment, or CLI permits content logging; omission, a declaration/pack default, explicit `False`, unresolved configuration, or an invalid value must not enable it. Respect normal precedence and retain value-source provenance. Local testing may explicitly set `LOG_CONTENT=True`.
- [ ] Apply the same gate to application/child-process diagnostic logs, Langfuse, and every tracing/export path in both api-agent and selected resource packs. Without explicit opt-in, omit actual user prompts and conversation turns, tool-call requests/arguments, tool responses, and responses to the user, including partial/streamed outputs. Treat all such content as potentially sensitive rather than attempting to recognize just known PII patterns.
  - [x] Implement the reusable `telemetry/privacy.py` boundary and owned-handler filter: validate explicit resolved external opt-in, allow typed operational metadata and registered runtime identifiers, scrub nested/serialized credential fields and registered secret values even with content enabled, avoid object/exception reprs, and reject unsafe numeric values. Composition owns the boundary and registers configured signing secrets. Synthetic tests cover these boundaries; attaching it to future handlers, provider callbacks, child logs, Langfuse and OTEL remains below.
  - [ ] Scrub conservatively at emission/export boundaries and avoid initially recording raw payloads when disabled. Use an allowlist of non-content operational metadata such as status, duration, token counts, and opaque correlation identifiers; inspect metadata fields for content-derived values rather than assuming field names make them safe.
  - [ ] Cover nested structures, serialized JSON, prompt/history/UI context, composed LLM prompts, tool inputs/results, response text/HTML, reasoning content, stream chunks, retry/failure paths, exception messages/reprs/stack-frame locals, HTTP/SDK debug logs, automatic instrumentation, and background flush/export. Do not allow another logger, trace attribute/event, resource-pack adapter, or error handler to bypass the gate.
  - [ ] Keep credentials, tokens, signing secrets, passwords, and TOTP values excluded under their existing rules even with `LOG_CONTENT=True`; this content flag does not relax authentication-secret handling.
  - [ ] Preserve real provider/tool execution and user-visible responses. This setting controls logging/tracing, not application behavior. Existing explicit Allure response/screenshot evidence is a separate test-artifact requirement; do not mirror its raw attachments into logs/Langfuse/traces when the gate is disabled.
- [ ] Wire Langfuse input/output and other trace content fields to the shared gate, including provider/node callbacks and automatic integrations. Verify disabled content is absent before transmission, not merely hidden by the report UI. Keep operational metrics available without content.
- [ ] Add deterministic tests for omitted configuration, defaulted values, explicit `False`, and explicit `True`, covering source precedence, pack defaults, strict boolean validation, and startup before configuration is resolved. Only explicit `True` should admit permitted content.
  - [ ] Seed distinctive content markers into every input/output category, nested object, exception, stream, retry, and resource-pack adapter. Capture all diagnostic log streams and exported Langfuse/trace payloads; assert that none of these markers or their serialized forms leak for omitted/default/False cases, including failure/cancellation and final flush. Verify useful non-content metrics remain.
  - [ ] Verify explicit `True` permits the intended local diagnostic content while credentials remain excluded. Add scoped integration checks of the real configured logging/trace adapters and provider instrumentation, without requiring a full rendered E2E scenario to verify scrubbing.
- [ ] Generate configuration/usage documentation explaining conservative default scrubbing and explicit local-test opt-in. Include this gate in manual review and the implementation report; no successful test of one logger proves all emission paths are covered.

- [ ] Apply the [provider boundary](provider_architecture.md) to every selected adapter: register provider-declared sensitive fields/values before routes, transports, logs or traces emit. Keep opaque tokens and credential values out even with LOG_CONTENT=True; retain necessary Allure response/error evidence without exposing authentication secrets. Verify synthetic provider emissions and failed setup/disposal paths.
