# Python TUI

## Checklist

- [ ] Implement the [pre-TUI worktree provenance gate](implementation_plan_a6.md) before all mode dispatch, including help, collect-only, and `NO_STD_IN`: compare the selected base and external-pack checkouts with their other registered worktrees. A stale selected checkout requires explicit stdin acknowledgement even under `NO_STD_IN`; every statement below about noninteractive shortcuts or never reading stdin applies after this gate has completed. Missing Git or unverifiable required worktrees fail with diagnostics.
- [ ] Use [Textual](https://textual.textualize.io/widget_gallery/) as the selected TUI library for the live selectable test list, scrollable failure screens, fixed key-help footer, and quit confirmation. Review remaining interface layout details with the user during planning.
- [ ] Allow unit tests to run interactively or through startup CLI arguments with `--no-std-in`. Integration and E2E execution require the interactive TUI and reject `NO_STD_IN=True` before prompts, prerequisite startup, or test execution. Unit tests remain deterministic without live LLM execution, are excluded from Allure, and must have a 100% pass rate for every commit; integration and E2E runs use [Allure reporting](implementation_plan_d.md).
- [ ] Build an option parser driven by the declarative configuration description. Resolve explicit values in increasing precedence: `.env`, environment variables, then command-line options.
  - [ ] Normalize CLI key hyphens and underscores to the same uppercase environment key: `--no-std-in` and `--no_std_in` both map to `NO_STD_IN`.
  - [ ] For boolean options, a bare flag means `True`. Accept both `--no-std-in=True` and `--no-std-in True`; accept `--no-std-in=False` and `--no-std-in False` to disable it. Apply the same behavior to the underscore spelling. Accept only the boolean values `True` and `False`, including from environment/config sources.
  - [ ] Support both `--key=value` and `--key value`. A value starting with `--` is not parseable as a value and is treated as another option key; document this limitation in the [README grouping plan](implementation_plan_c.md).
  - [ ] Require a declared type for every configuration value. Both the TUI and application must reject values that do not match the declared type.
- [ ] Add the single-hyphen exception `-h` as an alias setting `HELP=True`. Declare typed boolean `HELP` (default `False`) with normal `.env`/environment/`--help` support and strict True/False handling; other config options retain their double-hyphen syntax.
  - [ ] After the worktree provenance gate, resolve help before normal interactive configuration, required-value validation, mode dispatch, or service startup. When `HELP=True`, print help noninteractively and exit successfully, regardless of `NO_STD_IN`; do not read further stdin, save defaults, prompt for authentication or E2E acceptance, start processes, or run/collect tests. A stale checkout still requires the pre-gate acknowledgement, and a gate failure remains nonzero. Handle this shortcut through pack launchers as well as the base entry point.
  - [ ] Generate help from the executable declarations plus the command's special behaviors: mode names, `NO_STD_IN`, conditional required values/defaults, positional test selectors and their explicit-mode shortcut, `--collect-only`, E2E acceptance and retry restrictions, and operation exit statuses. Help must remain available without application credentials or a configured mode.
- [ ] Declare typed boolean `COLLECT_ONLY` (default `False`) with `--collect-only` / `--collect_only` and environment/config equivalents. In unit/integration/E2E modes, collect and list test identities without executing tests.
  - [ ] After the worktree provenance gate, if a test mode is explicitly supplied through `.env`, environment, or CLI, collection goes directly to terminal output with no interactive configuration, mode menu, test picker, or further stdin, even when `NO_STD_IN=False`. Apply positional selectors to filter the list; without selectors, list all applicable tests. Unit discovery includes base api-agent tests plus any selected-pack unit tests, de-duplicated by identity.
  - [ ] With no explicitly configured mode, interactive launch may select a test mode before listing; `NO_STD_IN=True` instead reports the missing mode. Reject collection for non-test modes. Validate only collection-relevant settings and selectors, not inference credentials or execution-only prerequisites.
  - [ ] Collection must not start app/container/UI prerequisites, call an LLM, request E2E run acceptance, record executed-test Allure/token/quota results, or replace the latest Allure run. Integration and E2E collection are allowed under `NO_STD_IN`; their execution requires interactive continuation, with the additional E2E human-acceptance warning. Return nonzero on collection/selector errors or an empty match, and do not enforce executed-test coverage for collect-only.
- [ ] Add deterministic tests proving help short-circuits before missing run configuration and that configured-mode collect-only never reads stdin after a completed worktree gate or executes tests/prerequisites, including filtered integration/E2E collection under `NO_STD_IN`. Cover the separate stale-checkout gate exception in its [grouping plan](implementation_plan_a6.md).
- [ ] Resolve `NO_STD_IN` before any interactive configuration step. When `True`, never read stdin after the worktree provenance gate or prompt for optional values or values with declared defaults; use the declared defaults when no explicit value exists.
  - [ ] Validate all configuration before starting the selected action. Report **all** missing required values without defaults in one error, showing the environment variable and `--` option for providing each one. Missing input must not cause an interactive fallback.
- [ ] Add the [interactive .env cleanup mode](implementation_plan_a1.md), listing effective values and `.env` presence with mark-for-delete and contextual `d` behavior.
- [ ] Add the [interactive unattended-auth setup mode and CLI credential helpers](implementation_plan_a2.md). On interactive launches with missing/empty required profiles, suggest setup with `s` to skip before normal mode selection and execution-specific configuration prompts; keep help/collect-only short-circuits noninteractive.
- [ ] When `NO_STD_IN` is absent or `False`, check which configuration values have explicit values from `.env`, environment variables, or CLI options; a declared default does not count as explicitly supplied.
  - [ ] Explain why newly encountered defaults require acknowledgement: the developer may know an override is needed, or may persist the current defaults into a solid point-in-time `.env` for reproducing/comparing/sharing a run's configuration. Exempt debug/account-index fields according to their declaration metadata; do not offer to persist them through this defaulting step.
  - [ ] List all unsupplied values with declared defaults in one step. Offer three choices: save their defaults to `.env`, use their defaults for this invocation without saving, or supply values individually. If saving is accepted, write those defaults to `.env`.
  - [ ] Ask for each remaining required value without an explicit value one at a time. The individual-values choice also prompts for the unsupplied defaulted values, showing `(default: <default>)` in each prompt. Optional values without defaults do not require a prompt.
  - [ ] Defer an unsupplied `TUI_MODE` to the main selection menu rather than asking for it as an ordinary required configuration value.
- [ ] After resolving the other configuration values, use an explicitly supplied `TUI_MODE` or present the first main TUI interaction: a selection menu containing "Run local", "Unit tests w/ coverage", "Integration tests", "E2E tests", "Allure serve", "Deployment logs", "Clear .env configuration", and finally "Setup unattended authentication". With `NO_STD_IN=True`, require `TUI_MODE` through configuration instead of presenting the menu.
- [ ] After choosing unit, integration, or E2E mode interactively, collect the available tests and show a selection screen before execution. Collection must not start application prerequisites or invoke an LLM.
  - [ ] Initially select every test. Put "All tests" first, highlighted and checked; allow toggling it off to clear the selection and pick individuals, or on to select everything.
  - [ ] List all grouping controls before individual tests: "All tests", then tag categories (for example Mutation tests), then test-file categories, then the full individual test list. Use repository-qualified identities for files/tests when unit discovery includes both the base and a pack. Support parametrized test identities.
  - [ ] Derive every group checkbox from its actual member selection: checked only when every member is selected. Toggling a checked group clears all its members; toggling an unchecked/partly selected group selects all its members. Recompute overlapping tag/file groups and "All tests" after every change; show selected/total counts for partial groups. Execute each selected test only once.
  - [ ] Provide an explicit action to start the chosen tests, and prevent an empty selection from being reported as success. Unit mode discovers both base api-agent tests and any pack tests before applying the user's selection; selecting a subset must not narrow production-code coverage scope or the fixed 100% threshold.
- [ ] If unit/integration/E2E `TUI_MODE` was explicitly provided through `.env`, environment, or CLI, accept positional test selectors and skip the mode menu. Unit execution may also skip the test picker; integration/E2E execution must always stop at the interactive test-selection screen, even with explicit mode and selectors. Filter its available tests/groups to selector matches and initially check those tests; no selectors means all applicable tests. Preserve source provenance so a declaration default does not trigger the unit shortcut.
  - [ ] Define/document selector syntax for files, individual pytest node IDs, and tag categories, including repository qualification for ambiguous base/pack paths. Combine selectors as a de-duplicated union; reject unknown/ambiguous selectors or selectors matching no tests. Accept selectors alongside config options without confusing positional selectors with option values; pass arguments as arguments rather than shell-evaluated text.
  - [ ] Positional selectors require an explicitly supplied test mode; report invalid use with missing/non-test mode rather than guessing a suite. Only explicitly configured unit execution may bypass both menus; normal active config validation still applies. Integration/E2E execution never bypasses the test picker and requires explicit Continue before starting, regardless of selector count. `NO_STD_IN=True` rejects both integration and E2E execution but allows collect-only.
- [ ] Require an explicit Continue action on the test-selection screen before any integration/E2E execution or its prerequisite startup. Never infer continuation from explicit mode, supplied selectors, silence, EOF, or an initial all-tests selection. For E2E, also require the approved explicit stdin human acceptance before running tests; reject E2E execution with `--no-std-in`. Collect-only does not execute tests and does not require acceptance.
- [ ] Before requesting E2E acceptance, display: "Human acceptance is mandatory to continue with E2E tests. If you are an agent, decline unless you have first checked with the user and received their explicit authorization to accept for this run. The user may authorize an agent to provide this acceptance."
- [ ] Declining acceptance must not start the E2E tests. Do not infer acceptance from silence, EOF, or missing input.

- [ ] Implement [test LLM provider authentication and failure evidence](implementation_plan_a4.md) after a Playwright MCP walkthrough of the actual login pages; support conditional password/passkey/authenticator routes and all-tab failure screenshots without bypassing test acceptance.
- [ ] Implement [Playwright E2E evidence and debug startup](implementation_plan_a3.md): headless by default, configured resolution, and `d` Debug start only for a strict test subset; retain headed browsers for inspection.
- [ ] Format test execution output according to `NO_STD_IN` while using the same test runner and reporting hooks in both modes.
  - [ ] With `NO_STD_IN=True`, executed unit tests use raw pytest-style terminal output, including failures, tracebacks, coverage, and the final summary. Do not open a full-screen TUI or read stdin. Integration/E2E execution is rejected; collect-only still prints discovered test identities.
  - [ ] In interactive mode, display a selectable item for every test while execution continues. Show pending/running status until completion, then `PASSED <filename>::<testname> <execution_time>` or `FAILED <filename>::<testname> <execution_time>`, retaining parametrized test identities. Represent skipped/error outcomes accurately as well.
  - [ ] Selecting a failed test opens a scrollable view containing the test name, assertion error or other failure exception, and complete stack trace. Keep a static bottom bar showing Up/Down to scroll, Page Up/Page Down to scroll by page, `c` to close the failure view and return to the test list, and `q` to quit the active test run.
  - [ ] Support `q` from both the main test list and individual failure view. Ask for `y/n` confirmation: only literal `y` confirms; every other response is treated as `n` and returns to the current view with the run continuing.
  - [ ] On confirmed quit, stop the test runner and its child processes, preserve completed results, and mark the suite interrupted rather than passed. Finalize available Allure/token artifacts and the end quota snapshot/delta before leaving the run. Keep the TUI responsive while tests execute.
- [ ] Add deterministic tests of raw versus interactive output routing, test-status updates, failure navigation, and confirmation/cancellation behavior without live LLM calls or a full E2E suite.

- [ ] Finalize test runs with a mode-specific results view, and provide the equivalent unit summary in raw `NO_STD_IN` output. Integration/E2E execution results remain interactive.
  - [ ] On the completed integration/E2E test-list and summary screen, show a static key-help bar with `c` to close results and return to the main menu, and `a` to switch immediately to "Allure serve". Pass the displayed suite's run ID to Allure so it opens that just-completed run, including failed or interrupted runs with finalized results. Keep `c` in a failure-detail view returning to the test list. No interactive shortcuts apply to `NO_STD_IN` output.
  - [ ] For unit tests, show whether tests passed and code coverage percentages, including each measured file/area and line/branch coverage where measured. Mark the summary red if any test did not pass or any single measured area has coverage below 100%, even when rounded display values would show 100%. The threshold is fixed and not configurable. Keep this coverage signal distinct from the requirement that every commit has a 100% unit-test pass rate and the final rewrite coverage target.
  - [ ] For integration/E2E, show `First-attempt passes: <passed>/<total tests> (<percentage>%)` first. Only for E2E with confirmation reruns enabled, also show `Final passes including retries: <passed>/<total tests> (<percentage>%)`. Count unique selected test identities, not attempts; skipped/not-run tests are not passes. Mark interrupted/incomplete runs explicitly, and show N/A for percentages if no tests were selected.
  - [ ] Show whole-suite user-prompt count alongside provider-reported token counts, optional quota usage, and the provider's estimated total cost and cost per prompt. Count initial prompts, clarification answers, and mutation approvals as separate user prompts, including prompts in failed attempts and confirmation reruns. Do not count internal node/LLM calls as user prompts; show cost per prompt as N/A when the prompt count is zero.
  - [ ] When available, show starting and final quota percentage used, their difference, and the final quota reset datetime in UTC with its remaining hours/minutes/seconds. Obtain cost estimates through the LLM provider's cost-estimation function. Preserve unavailable/reset/concurrent-usage qualifications from the [usage plan](implementation_plan_f.md).
  - [ ] Display optional quota fields only when supplied by the LLM provider. Report unavailable cost estimates explicitly. Validate result formatting and cost-per-prompt arithmetic deterministically using provider fixtures.

- [ ] Resolve a launch context before selecting a test suite: selected resource-pack root, test-owner repository root/name, mode-specific test paths, and configuration/output roots. Have launchers supply their own roots explicitly rather than treating the process working directory as the suite identity.
  - [ ] An api-agent launch defaults to the demo resource pack. Unit mode always runs api-agent's `tests/unit` plus any demo-pack unit tests. Integration/E2E modes use the selected pack's declared suites, with the demo declaration pointing to the appropriate api-agent tests. Demo pack location and test-owner location are distinct.
  - [ ] A resource-pack launch passes its repository root as `--resource-pack-dir`. Unit mode runs api-agent's unit suite and the selected pack's unit suite if present; integration/E2E modes run only the suites declared by the selected pack. Declare pack paths relative to its pack/test-owner root, resolve them to absolute paths, and run each repository's tests with its own working directory and pytest configuration through the shared runner.
  - [ ] Explicit resource-pack selection takes precedence over launcher defaults. Unit mode always includes the base api-agent suite and adds any selected-pack unit suite; de-duplicate identical resolved test paths. Integration/E2E stay scoped to the selected pack's declarations. Pack unit tests are optional, including for data-only packs, and their absence is not a failure. Validate explicitly declared suite paths and report a missing/empty base unit suite as a configuration error rather than presenting zero tests as a successful unit run.
  - [ ] Use each suite's repository identity for Allure labels, artifact ownership, coverage scope, and suite accounting. In combined unit mode, show results and coverage for the base and any pack code separately, with one final status: any failure or any measured area below 100% marks it red. Do not let aggregate coverage hide an uncovered area; a pack with no production code has no pack-code coverage percentage to enforce. Show repository/pack/mode in the TUI so the user can see which suite will run. Keep screens, retry controls, and reporting code shared across launchers.
  - [ ] Test suite selection deterministically from both launchers, from unrelated working directories, and with explicit pack overrides and relocated base-service paths. Cover base-plus-pack unit execution, absent pack units, path de-duplication, combined failure/coverage status, and selected-pack-only integration/E2E execution.

- [ ] Apply [hierarchical defaults and conditional settings](implementation_plan_b.md) during interactive configuration: shared defaults, then selected-pack default overrides, then explicit `.env`/environment/CLI values. Show each applicable default's source when offering to save/use/change defaults. Resolve controlling settings before asking about dependent settings; skip inactive feature configuration. With `NO_STD_IN=True`, validate all active requirements without stdin.
- [ ] Use the [shared prerequisite manager](implementation_plan_h.md) to start selected container profiles and optional host Nx UI for local/integration/E2E actions, reporting readiness and logs in the TUI. Unit mode runs deterministically without starting these prerequisites. Preserve E2E acceptance before starting any E2E execution.

- [ ] Implement [local-run authentication](implementation_plan_a5.md): no startup test-auth preflight, an explicit pack-owned authenticated-UI action, and lazy authentication through the selected LLM provider before returning authentication challenges.
- [ ] Declare `RUN_LOG_SOURCE` / `--run-log-source` (also `--run_log_source`) for local-run mode using stable source names, never menu numbers. When not otherwise configured, default to `all` with `NO_STD_IN=True` and `agent` interactively. Explicit `.env`/environment/CLI values override those defaults and determine the initial source in both modes.
  - [ ] Use `all` for live interleaved service/component-labeled output; a specific source such as `agent`, `ui`, `api`, `database`, or `langfuse` emits only that source's raw logs without added source labels. Preserve the original log content. Register conditional/additional source names from the launched services and expose them in the interactive log menu and generated docs.
  - [ ] With `NO_STD_IN=True`, stream the resolved source to terminal output without menus or stdin. Interactive mode retains `l`/number shortcuts and `*` for switching after startup, irrespective of the configured initial source. Validate unknown names, numeric values, and sources unavailable under the selected feature combination as configuration errors rather than silently selecting another source.
- [ ] In interactive "Run local" mode (`NO_STD_IN` absent/False), start the main view following the resolved `RUN_LOG_SOURCE` (default `agent`) and show static help for `b` (browser destinations) and `l` (log sources).
  - [ ] Pressing `b` opens a numbered menu: `1: UI` with its full resolved address, `2: Agent` with its full address at root `/`, and `3: Langfuse` with its full address only when Langfuse is enabled. Number keys open the selected destination in the host's default browser, including host forwarding from Distrobox. Use actual configured/ready endpoints rather than guessed ports; show an unavailable UI destination if neither a launched UI nor an external UI URL exists.
  - [ ] Pressing `l` opens a numbered menu of available log sources, with Agent first and conditional sources for the UI, upstream API, database, Langfuse, and any other prerequisites the run launched. Number keys switch the main view to follow the selected source live. A remote-only service without a local log stream is not a selectable log source; single-source views preserve raw log content without added source labels; the all-logs view adds service/component labels.
  - [ ] Put `*: All logs` at the end of the `l` log-source menu. Pressing `*` switches to a live interleaved view of every available run log stream, labeling each entry with its service/component. Preserve order within each source and use receipt order across sources; keep following newly arriving output.
  - [ ] Keep service log capture running while another source is viewed or a menu is open, and keep the selected view following new output without restarting services. Display the current log source; allow closing either menu to return to that view without changing it. `NO_STD_IN=True` does not present these menus or read hotkeys.
  - [ ] Add deterministic coverage for conditional default/explicit named log-source selection, conditional numbered menus, resolved browser URLs, log-source switching, source-labeled interleaved all-logs output, and absence of interactive controls under `NO_STD_IN`, without opening a real browser or starting prerequisite stacks.

- [ ] Make `TUI_MODE` conditionally required when `NO_STD_IN=True` and help is not requested; missing mode/config is an error with no prompt. Collect-only validates collection requirements rather than execution requirements. Return an operation-based process exit status, rather than always reporting successful TUI shutdown.
  - [ ] Unit mode exits nonzero for any test failure, execution/collection error, or any measured production-code area below 100% coverage. Integration has no reruns and exits nonzero if any test fails. E2E uses the configured confirmation protocol and exits nonzero if any initially failing test does not recover through all allotted consecutive confirmation passes.
  - [ ] Preserve nonzero status for invalid selectors, empty collection/selection, failed startup, and early cancellation. Closing results or viewing Allure must not turn a failed test operation into success. Report skipped/not-run tests accurately without treating them as passes.
  - [ ] Local application and Allure modes wait for the launched operation to terminate and forward its exit code (or conventional signal-derived status), including after user termination. Cleanup/logging must not mask the operation's status; prerequisite startup failures remain nonzero.
- [ ] Add deterministic tests for initial/group/overlapping selection behavior, explicit-mode positional selection, missing conditional mode, per-mode exit status, and child-process status forwarding. Verify integration/E2E always show a selector-filtered picker and wait for explicit Continue, and reject `NO_STD_IN` execution without reading stdin or starting prerequisites while still allowing collect-only. No live LLM or full E2E run is needed to validate these controls.
