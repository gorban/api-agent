# Allure reporting and persistent test results


## Checklist

- [ ] Establish Allure output before the first rewrite integration or E2E test, including the initial "Ok" milestone. Record integration and human-accepted E2E runs through the interactive TUI only, after explicit continuation from the test picker. Neither execution mode supports `NO_STD_IN`; collect-only is not a recorded test run. Unit tests must never be Allure-recorded: disable Allure collection/writers for unit mode, create no Allure result files or S3/secondary Allure uploads, and leave the latest integration/E2E run unchanged. Unit pass/coverage reports belong to local output and CI checks.
- [ ] Organize Allure results as `<repo> -> <test mode: integration / E2E> -> <test file name> -> <test>`. Map repository, test mode, and test file to the suite hierarchy and retain individual test names. Use the test mode selected through `TUI_MODE`; keep LLM provider authentication configuration separate.
  - [x] Implement and deterministically verify the repository/mode/file/test Allure hierarchy in `src/api_agent/testing/recording.py`, including UUID run identity, attempt labels, test durations, failed/interrupted suite results and fail-closed manifest metadata. Real E2E attachments remain below.
  - [ ] Verify this hierarchy explicitly: the reference artifact-upload commit establishes staging/persistence, work with the user to come up with explicit explicit parent-suite/suite/sub-suite labeling
- [x] Add deterministic checks proving unit execution never initializes Allure recording/storage, writes or uploads Allure artifacts, or replaces the latest recorded run, including shared-runner use.
- [ ] Keep unit tests deterministic and independent of live LLM execution. Require a 100% unit-test pass rate for every commit; this is distinct from the final 100% code-coverage target.
- [x] Implement controlled-adapter S3 persistence/history in `src/api_agent/testing/storage.py`: immutable conditional writes, identical-byte retry, digest validation, manifest-last publication, parsed timestamp ordering, rejected unsafe secondary paths and bounded SDK calls. Deterministic fake-S3 checks pass; actual AWS/LocalStack persistence and the viewer remain unverified.
- [ ] Persist all Allure results in S3 from the initial "Ok" milestone onward, retaining successive runs as a history of implementation development rather than overwriting earlier runs. Use LocalStack for local S3 testing.
- [x] Declare `ALLURE_S3_USE_LOCALSTACK=False`; True conditionally defaults bucket `allure-results` and endpoint `http://localhost:4566`, preserving explicit bucket/region overrides. The scoped lifecycle provisions and verifies the selected bucket before publication. Synthetic CLI and planner checks prove idempotence and failure propagation; actual S3/history verification remains open.
- [x] Add optional typed configuration for a secondary Allure results destination, such as a local directory. When configured, write results there as well as to S3; it must not replace primary S3 persistence.
- [ ] Provide the TUI's "Allure serve" mode for viewing test results. Default to the most recent recorded integration/E2E run for the selected repository/pack; unit runs must not replace that selection.
  - [ ] After the report server is ready, automatically open its URL in the host's default browser, including when entering Allure mode through the `a` shortcut. Support host-browser forwarding when the TUI runs inside Distrobox. Also display the URL; if browser opening fails, keep the report available and report the opening failure.
  - [ ] Track completed/finalized run identities in persistent history and resolve the latest run from run metadata, not arbitrary file modification times or stale cached reports. Load the selected run's artifacts locally or from S3 as needed without combining results from unrelated runs.
  - [ ] Support `a` from the completed test-list/summary screen as an immediate transition into Allure mode, pinned to that screen's run ID. A concurrently completed run must not redirect this shortcut away from the results the user was viewing. If no recorded run exists, show that clearly.
  - [ ] Test latest-run selection and the results-to-Allure transition deterministically, including failed/interrupted finalized runs, newer concurrent runs, and a subsequent unit run.

- [ ] Before the first integration/E2E run, establish [token and suite-wide quota tracking](implementation_plan_f.md). Retain usage CSV artifacts and before/after `pctUsed` snapshots and delta with each run, and include the suite delta in TUI results.

- [ ] Require [Playwright UI evidence](implementation_plan_a3.md) for every E2E run: original `response_text` and `response_html` when present, plus rendered screenshots after maximizing the agent modal and scrolling to the top. Retain both outputs and complete scroll-region evidence where needed, including debug and confirmation attempts, under the correct test/run identity in S3 history.

- [ ] Record [unattended-auth and general Playwright failures](implementation_plan_a4.md) with current-state screenshots of every accessible open tab before response capture/teardown. Include suite-auth setup failures and failures with no agent response, retaining tab/URL/test/attempt identity in Allure and persistent S3 history.

- [ ] Before live recording, automatically request the `reports` dependency group through shared environment preparation. Keep help, collection and unit execution independent of boto3. Exercise LocalStack upload/retry/history with actual S3-compatible responses before treating persistence as live-verified.
- [ ] At the live runner boundary, register newly issued bearer/access/refresh/password/TOTP values on the shared evidence boundary before results can emit. Sanitize raw event/output callbacks and binary browser attachments through their approved evidence path. Allure evidence is separate from `LOG_CONTENT` diagnostic exports; credential scrubbing always applies.
